# 打包与分发：内置 JRE 的桌面安装包

桌面端只有 `ai-shell.exe` 一个入口，后端 fat jar 和一份裁剪过的 Java 运行时作为 Tauri resources 一起安装：Windows 上资源目录就是可执行文件所在目录，安装后布局为 `<app>/ai-shell.exe`、`<app>/backend/backend.jar`、`<app>/backend/runtime/`。**Why**：用户机器不一定装了 Java 21，也不能要求他们自己配 `AI_SHELL_BACKEND_JAR`；把运行时和 jar 放进安装包，应用启动即可自洽。Tauri 的 `bundle.resources` 映射（`../backend/target/backend-0.0.1-SNAPSHOT.jar → backend/backend.jar`、`../backend/target/runtime → backend/runtime`）在安装器里原样保留目录结构（bundler 对目录源 walking 后按 `strip_prefix` 重建目标路径，glob 源则会被拍平，所以这里不用 glob）。

Rust 侧 `resolve_java` 的解析顺序：`AI_SHELL_JAVA`（开发调试/覆盖）→ `<resource_dir>/backend/runtime/bin/java.exe` → PATH 上的 `java`；`resolve_jar` 保持原有顺序：`AI_SHELL_BACKEND_JAR` → 开发目录 `backend/target/backend-0.0.1-SNAPSHOT.jar` → `<resource_dir>/backend/backend.jar`。**Why**：开发时直接跑 `tauri dev` 不应被资源目录约束，而打包后若没有显式覆盖就必须用内置运行时，避免“机器上恰有一个不兼容的 java”导致启动失败。

`scripts/package.ps1` 负责整条流水线：`mvn -o package`（默认跑测试，`-SkipTests` 可跳过）→ `jlink --add-modules … --strip-debug --no-header-files --no-man-pages --compress=zip-6 --output backend/target/runtime` → `npm run tauri -- build`（默认 `--no-bundle`，`-Bundle nsis` 产出安装器）→ 组装 `release/AI-Shell-<version>-win-x64/`（exe + backend.jar + runtime + README）并打 zip。jlink 模块集包含 `java.sql`（SQLite JDBC）、`java.naming`/`java.management`（Spring）、`jdk.crypto.ec`（TLS ECDHE）、`jdk.unsupported`（Netty 等用 `sun.misc.Unsafe`）、`java.desktop`/`java.instrument` 等 Spring Boot 常见隐式依赖；**Why**：`jdeps` 无法可靠分析 Spring Boot fat jar 里嵌套 jar 的模块依赖，宁可多带几个模块（运行时 49 MB），也不能在用户机器上出现 `NoClassDefFoundError`。产物不再写进 `dist/`：那是 Vite 的输出目录，`vite build` 会先清空它，之前把便携包放进去直接导致 `EPERM`。前端构建用 `manualChunks` 把 `@xterm/xterm` 与 `addon-fit` 拆成独立 chunk（应用 250 KB + xterm 331 KB），既消除了 Vite 的 500 KB 警告，也让终端引擎在升级应用代码时保持可缓存。

验证中发现并修掉四个打包才会暴露的问题：

1. **启动竞态**：`ConnectionsPane` 只在挂载时请求一次主机列表，后端还在 `starting`（打包机冷启动约 3.4 s）时拿到“后端尚未就绪”，之后永不重试，左下角一直红字。改为在挂载时轮询 `backend_info`，只有 `ready` 才拉列表，`failed` 显示错误。**Why**：状态栏自己每 3 s 轮询，左栏却是一次性请求，两个组件对“后端尚未就绪”的处理不一致。
2. **强杀残留后端**：Windows 上 `Stop-Process -Force` 终止 `ai-shell.exe` 不会执行 Rust 的 `Drop`，子进程 `java.exe` 继续持有 jar、端口和 SQLite 文件（验证时确实留下了一个孤儿进程，并让下一次前端构建报 `EPERM`）。`Sidecar::spawn` 现在把子进程放进 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 的 Job Object，作业句柄随进程一起被系统关闭时，整棵子进程树被回收。**Why**：桌面应用崩溃/被任务管理器结束是常态，不能靠正常退出路径兜底。
3. **打包后用错 jar**：`resolve_jar` 原来把 `env!("CARGO_MANIFEST_DIR")` 拼出的开发路径排在包内 jar 之前，而这条路径是编译期绝对路径，在构建机上永远存在——从仓库目录启动便携包时，子进程实际加载的是 `backend/target/backend-0.0.1-SNAPSHOT.jar` 而不是包里的 `backend/backend.jar`。改为 release 构建优先 `<resource_dir>/backend/backend.jar`，只有 debug（`tauri dev`）才保留开发路径优先。**Why**：发布产物必须自洽，不能被构建机上的残留文件覆盖；开发迭代又需要 `tauri dev` 用最新 jar。
4. **Windows verbatim 路径**：修好第 3 条后，包内 jar 才第一次真正被用上，随即暴露 `java -jar` 打不开 `\\?\E:\...` 形式的路径（Tauri `resource_dir()` 返回 verbatim 前缀，JVM 报 `ClassNotFoundException: org.springframework.boot.loader.launch.JarLauncher`）。新增 `plain_path`，把 `\\?\` / `\\?\UNC\` 还原成普通路径后再交给子进程，并加了 Windows 单测。**Why**：这两个问题叠在一起，之前“便携包能启动”其实是构建机上的开发 jar 在兜底，包内 jar 从未被真正执行过。
