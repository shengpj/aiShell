# 对话按主机落 SQLite

对话以 Host（`地址:端口`）为键，而不是终端会话 id：`TerminalBridge.open` 校验目标后记录 `conversationKey`，`TerminalSessions.conversationKey(sessionId)` 把它交给 `ChatController`，`ChatService` 用这个键作为 ADK session id。断开重连、换一个终端窗口、后端重启，只要还连同一台 Host，就回到同一个 Conversation。**Why**：GLOSSARY 把 Conversation 定义为“围绕一台 Host 持续存在、跨 Session 存活”，此前用临时终端 id 作键，每次重连都从空对话开始，模型也看不到上一轮的上下文；Host 是唯一稳定且有业务含义的身份，profile 与手工输入都归一到同一个键。终端会话仍只用于绑定 `runCommand` 工具，会话一断 AI 命令就无处可执行。

ADK 会话原本只有 `InMemorySessionService`（ADK Java 无 SQLite 实现）。新增 `SqliteAgentSessionService implements BaseSessionService`，在同一个 `AI_SHELL_DATA_DIR/ai-shell.db` 里建 `agent_session` 与 `agent_event` 两张表；事件用 ADK 自带的 `Event.toJson()` 落库、`Event.fromJsonString(..., Event.class)` 还原，`getSession` 支持 `GetSessionConfig` 的 `numRecentEvents` 与 `afterTimestamp` 过滤，`appendEvent` 同时把 `stateDelta` 应用到 session state 并更新 `updated_at`。**Why**：用 ADK 官方序列化而不是自写字段映射，工具调用、functionResponse、partial、timestamp 等结构才能原样回放；Runner 在下一轮通过 `getSession` 拿到的就是上一轮的真实事件，模型上下文自然延续。不复用 ORM：项目里 Host 存储就是“每操作一条 JDBC 连接 + WAL”的写法，保持一致。

用户可见的聊天记录单独存 `chat_message`（`ChatTranscriptStore`），不复用 ADK 事件：`ChatChannel.send` 增加一个 `Sink`，SSE 每发出一帧就同步写一行投影——`user`/`ai`/`error` 存纯文本，`command` 存与前端收到的同一份 JSON 负载（`state`、`command`、`exitCode`、`durationMs`…），并用 `command`+`state` 列在 `started → finished` 时原位更新同一张卡片。连续流式文本按 `turn_id` 合并进上一条 `ai` 气泡，遇到命令卡片或错误就另起一条。**Why**：前端渲染规则（气泡合并、命令卡片状态迁移）已经在 `ChatPane` 里实现，历史接口只要回放同一形状的数据就不需要第二套渲染逻辑；ADK 事件里既有 partial 分片也有 functionCall/functionResponse，直接拿它当 UI 数据会重现“把每个分片各画一条”的旧问题。写投影失败只记日志，不影响本次对话（持久化是旁路，不是链路前提）。

接口：`GET /api/chat/history?session=<live session>&limit=<n>` 返回 `{conversation, entries, truncated}`，`limit` 默认 200、限制在 1–1000，只取最新的 n 条（按 id 升序返回），被截断时 `truncated=true`；`entries` 与 SSE 帧同形（`{id, kind:"user"|"ai"|"error", text}` 或 `{id, kind:"command", command, state, exitCode, durationMs, message?, reason?, timeoutSeconds?}`）；要求 `chat` 用途 ticket，终端不在线返回 409，缺 `session` 返回 400。前端 `ChatPane` 在 `sessionId` 变化时先清空，再拉历史并恢复条目，`nextId` 取历史最大 id + 1；加载期间输入框禁用，失败会重试 3 次（间隔 800 ms），仍失败才在底部提示“历史对话加载失败：…”，不阻塞后续对话；`truncated` 为真时提示只显示了最近条目。**Why**：历史只在“有活动终端”时才有意义，和聊天、文件树使用同一套生命周期；id 用数据库自增主键，刷新后 key 稳定，恢复的卡片不会与新增条目撞号。

**验证状态**：后端 105 个测试全绿（2 个 live spike 跳过），本轮新增 13 例：`SqliteAgentSessionServiceTest` 5（创建/读取 state、换实例后事件仍在、listEvents/listSessions、`numRecentEvents` 截断、删除连带事件）、`ChatTranscriptStoreTest` 4（AI 分片合并与命令/错误断泡、finished 原位更新、refused 独立卡片、会话隔离）、`ChatEndpointTest` 新增 4（history 恢复 user/command/ai 且顺序正确、无 ticket 401、未知会话 409、ADK 事件同时落库且包含 user 与 ops_assistant 两类 author），`TerminalWebSocketTest` 增补 1 处断言（`opened` 后 `conversationKey` 为 `127.0.0.1:<port>`）。真实主机 `121.41.177.215` 验证：首轮 `POST /api/chat` 后 `history` 返回 `conversation="121.41.177.215:22"` 与两条记录（user + 模型错误；live 环境未配有效 API key，刻意指向不可达端点让模型调用快速失败），SQLite 中 `agent_session` 有该会话、`agent_event` 有 user 事件；随后杀掉后端、用同一数据目录重启，重新建立 SSH 终端（新 session id）后 `history` 仍返回完全相同两条记录；Chrome + `__TAURI_INTERNALS__` 桩下连接主机后 AI 面板直接显示这两条历史，界面“断开→再连接”后再次恢复且不重复。**新对话/清空会话（2026-10-28）**：`conversation_epoch(host_key, epoch, updated_at)` 表持久化每个 Host 的当前会话序号。`ConversationStore.current` 返回当前 key（epoch 1 仍沿用 `host:port`，已有历史原样可读），`POST /api/chat/reset`（chat ticket，`{session}`）把序号 +1 并返回新 key（例如 `121.41.177.215:22#2`）；`/api/chat` 与 `/api/chat/history` 都通过 `current` 解析，所以新一轮 ADK session、聊天记录与历史恢复自然切到新 key。前端 AI 面板右上角加“新对话”按钮，先用原生确认框二次确认，成功后清空面板并在底部提示新 key；旧 ADK session 与 `chat_message` 保留在库里，只是不再是当前会话。终端未连接或该 session 正有回合在跑时返回 409。**Why**：按 Host 持久化会让换话题时模型继续带着旧上下文（连历史里“不要运行任何命令”这类指令都会延续），必须有一个显式的新会话入口，同时不能删审计与历史数据。agent instruction 同时明确“只回答最后一条消息、不要复述历史命令、历史里的限制只对当轮有效”，降低模型把旧指令带进新话题的概率（提示词只能降低概率，不能替代新会话）。

验证：`ConversationStoreTest`（默认 key、轮转、重开实例后保持）；`ChatResetEndpointTest` 使用独立数据目录（重置后新 key 的历史为空、旧 ADK session 仍在、后续回合落到新 session、未知会话 409、无 ticket 401）；原生窗口实测：连接后点“新对话”→ 原生确认 → 提示 `121.41.177.215:22#2` 且面板清空，重启应用重连后面板仍为空（旧对话仍在库里）。后端 114 个测试全绿（含历史限量与审计轮转的 3 个新用例）。

**已补验**（2026-10-28，ADR 0013）：在打包版上把有效的 `DEEPSEEK_API_KEY`（仅注入本次进程环境，未落盘）交给 sidecar，首轮让 AI 执行 `echo NATIVE-AI-OK`；随后关闭应用与后端进程，重新启动并重连同一 Host，AI 面板恢复 4 条历史，追问 “which command did you run earlier…” 时模型回答 `You ran: echo NATIVE-AI-OK`——上一轮的工具调用事件确实被重新加载为模型上下文。

**已知取舍**：`conversationKey` 只含主机与端口，同一台机器上的不同账号共享一个 Conversation（符合 GLOSSARY 的 Host 语义）；“新对话”对整个 Host 生效，同 Host 的其他终端也会切到新会话，旧对话在界面上不可见（只能查库），序号只增不减；同一 Host 同时开两个终端并各自发起对话不会被串行化，可能交错追加 ADK 事件，UI 也按到达顺序合并；历史接口只返回最近 200 条（前端提示“仅显示最近 N 条，更早记录仍在数据库中”），更早的条目只能查库；ADK partial 分片按官方序列化原样保存，若上游在截断/重试时落库了半截事件，下一轮上下文可能重复一小段文本；删除 Host 不会删除对应会话与聊天记录（与审计留存一致）；关闭自动清理/轮转尚未实现。
